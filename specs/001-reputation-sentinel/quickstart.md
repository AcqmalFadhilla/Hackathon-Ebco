# Quickstart: Reputation Sentinel Ops

Validation guide for the MVP — proves the 4 user stories end-to-end. Not an implementation
guide (see `tasks.md`, once generated by `/speckit-tasks`, for build steps).

## Prerequisites

- Python 3.11+ environment with project dependencies installed (ADK, `google-genai`,
  Streamlit, `google-api-python-client`, `tenacity`) — see `research.md` for why each was
  chosen.
- Access to the team's GCP hackathon sandbox project (Gen AI model + Firestore + Secret
  Manager + Cloud Scheduler enabled), with your manager identity added to the
  Identity-Aware Proxy allow-list (`research.md` → Manager Authentication / Access Control).
- The seed/sample review dataset toggle available as a fallback (`research.md` → External
  API Resilience) if live GBP OAuth access isn't ready yet.

## Setup

1. Configure environment/config for the target GCP project (Gemini access, Firestore,
   Secret Manager, Cloud Scheduler) per `src/config/settings.py`.
2. Run the Streamlit app (`src/ui/app.py`) — this is the single deployable entrypoint
   (Project Structure in `plan.md`). Behind IAP, this resolves your authenticated identity
   to a `Manager` record (FR-019).
3. Connect at least 2 demo branches using the in-app connect flow (FR-001, real OAuth via
   `src/integrations/gbp_oauth.py`), or enable the seed-data toggle for branches where live
   access isn't ready.

## Validate User Story 1 — Unified Multi-Branch Review Inbox (P1)

1. Trigger ingestion via the manual "sync now" button, or wait up to 15 minutes for the
   Cloud Scheduler-driven automatic cycle (SC-001) to cover both demo branches.
2. Open the inbox view in the UI.
3. **Expected**: reviews from both branches appear in one list, each tagged with sentiment
   (positive/neutral/negative) and topic(s) — no draft or publish action taken yet.
4. Filter by branch, then by sentiment — confirm the list narrows correctly.
5. Ingest (or seed) a review that already has an existing owner reply.
6. **Expected**: it appears in the inbox marked as already-answered and never enters the
   draft-and-approve flow (FR-020).

## Validate User Story 2 — AI-Drafted Reply with Manager Approval (P2)

1. Open a review from the inbox.
2. **Expected**: a draft reply is already present.
3. Edit the draft (optional), then Approve.
4. **Expected**: the UI shows the publish attempt result and confirms `published` once the
   publication state check (contracts/gbp-api-usage.md) passes.
5. Repeat on a different review but Reject instead.
6. **Expected**: no reply is published; the review returns to a pending-response state with
   a freshly generated draft (data-model.md Review state machine).

## Validate User Story 3 — Urgent Review Escalation (P3)

1. Ingest (or seed) a review with clearly severe/urgent content (e.g. 1-star + safety
   complaint keyword).
2. **Expected**: it is flagged "urgent" and shown separately from routine reviews in the UI,
   and the assigned manager sees an in-app alert — independent of whether its draft has been
   approved yet.
3. Ingest a routine, mildly negative review.
4. **Expected**: no urgent alert; it flows through the normal draft-and-approve path only.

## Validate User Story 4 — Cross-Branch Review Health Digest (P4)

1. With reviews present across both demo branches (mixed sentiment/severity), request the
   digest from the UI.
2. **Expected**: branches are ranked by health score (worst to best) with each branch's top
   recurring complaint topics listed, returned in under 30 seconds (SC-005).

## Resilience check (Principle IV)

1. Temporarily point the GBP client at an invalid endpoint/credential (or disable network).
2. Trigger an ingestion cycle.
3. **Expected**: no crash; the system falls back to the seed/sample dataset (or clearly
   surfaces `Branch.connection_status = "error"`) rather than failing the whole demo.

## Approval-gate check (Principle I — must never fail)

1. Inspect the codebase for any path that calls the GBP reply-write client without first
   passing through a recorded manager-approval action.
2. **Expected**: none exists. This is a hard constitutional requirement, not a preference.

## Authentication check (FR-019 / SC-007 — must never fail)

1. Attempt to open the deployed Cloud Run URL without an IAP-authorized identity (e.g., an
   incognito session not on the allow-list, or curl without an identity token).
2. **Expected**: access is denied before any review data or action is reachable — no review
   list, no draft, no approve/reject/publish action is exposed to an unauthenticated request.
3. As an authorized manager, approve one review's draft.
4. **Expected**: the recorded `approved_by` on the Draft Reply matches your authenticated
   identity (`Manager.google_identity_email`), not a manually-entered value.
